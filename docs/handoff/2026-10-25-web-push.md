# Handoff — Web Push in notify-flow

## Obiettivo

Le piattaforme che usano notify-flow hanno una messaggistica interna. Quando un utente riceve un messaggio e non sta guardando quella chat, il browser deve mostrargli entro pochi secondi un avviso come "Piattaforma XX — Hai ricevuto una notifica da Marco", anche a webapp chiusa.

È un canale separato dalle email, spento di default e acceso per singolo client. notify-flow non vede né salva mai i messaggi: fa solo comparire l'avviso.

## A che punto siamo

Il codice è finito sul branch `feat/web-push`: 13 commit sopra `main`, da `f3cb0df` (spec) a `2e97077`. Il branch non è pushato né mergiato.
- **Test e build:** `npm test` 216/216, verde per 10 run di fila. `npm run typecheck` e `npm run docs:build` sono puliti.
- **Revisioni:** tutti i 5 task del piano sono passati da implementatore e revisore (subagent-driven). Anche la revisione finale del branch è chiusa, con le sue correzioni applicate e riverificate.
- **Ancora da fare:**

  - il deploy: chiavi, variabili, secret, migrazione remota.

## Cosa abbiamo provato che NON ha funzionato

- **Il service worker che salta l'avviso a chat aperta.** Era la prima idea, ma Safari revoca l'iscrizione dopo circa 3 push che non mostrano nulla. La regola "chat aperta, niente push" vive quindi nel backend della piattaforma, e il service worker mostra sempre la notifica.
- **Il test del limite IP con richieste reali** (`test/router.test.ts`). Con 600 richieste di fila scavalcava la finestra di 60 s del limitatore e falliva circa 1 volta su 6. Ora usa un limitatore finto.
- **Un `try` largo intorno al fetch push.** Catturava anche gli errori di firma VAPID e di D1, che finivano registrati come "network" e ritentati. Ora dentro il `try` c'è solo `fetchPush`.
- **`fetch` con i redirect di default.** Un 3xx da un host consentito avrebbe ripostato il payload altrove (SSRF). Ora si usa `redirect: "manual"`.

## Problemi incontrati e come li abbiamo risolti

- **Il tipo ECDH nei tipi Workers.** I tipi generati chiamano la chiave peer `$public`, mentre il runtime usa `public`. Due chiamate `deriveBits` fanno un cast documentato in `src/push/crypto.ts`.
- **Un secret opzionale non tipizzato.** `VAPID_PRIVATE_KEY` non è in `secrets.required`, quindi non compare nell'`Env` generato. `vapidKeys()` lo legge con un cast commentato.
- **Un import ciclico.** `vapidKeys` e `pushConfigured` stanno in `crypto.ts` e non in `routes.ts`, perché `routes.ts` importa `sender.ts`.

## Decisioni prese

Decise con l'utente:
- **Nessun testo scritto dagli utenti nella notifica,** nemmeno come anteprima, in questa fase. Si mostra solo il mittente.
- **Chat aperta:** se la chat è aperta il backend non chiama notify-flow. Se è aperta sul PC, nemmeno il telefono suona.
- **Dove stanno i dati:** i messaggi restano nel database della piattaforma. In D1 stanno solo iscrizioni, interruttore e registro senza contenuti. È stata scartata l'alternativa di far tenere le iscrizioni alla piattaforma.
- **Limiti:** 600 al minuto per client sulle push (`PUSH_RATE_LIMITER`), separati dalle email, e limite per IP a 600, scendendo dai 1000 proposti.

Scelte mie, approvate dentro la spec:
- **Template e invio:** solo il template integrato `new-message`, senza API per template push. L'invio è solo sincrono, senza coda.
- **Variabili:** al massimo 64 caratteri ciascuna.
- **Clic sulla notifica:** apre un percorso relativo del sito della piattaforma, mai un link esterno.
- **Conversazione:** `tag` è la conversazione e serve sia come `Topic` sia come notifica unica per chat.
- **Dispositivi:** al massimo 10 per utente. Limite orario: 60 per utente e conversazione.
- **Host consentiti:** FCM, Mozilla, WNS e Apple. C'è una sola coppia VAPID per tutto il servizio.

Rimandate:
- **Formato delle chiavi VAPID:** non viene validato.
- **`docs/api-reference.md:75`:** dice ancora "never blocks email", ma il limite per IP è condiviso.
- **Esempio di logout:** non dice di chiamare il backend prima di chiudere la sessione.
- **Rifiniture minori** giudicate "possono aspettare" dalla revisione finale: il nome di `TextEncoder`, `extractable` sulla chiave effimera, alcuni test che potrebbero coprire di più.

## Dove vogliamo andare

1. Lancia `npm run dev`, apri `/admin/` e prova l'interruttore nella sezione Clienti. Con `VAPID_*` vuote deve comparire l'avviso "Web Push is not configured" e l'interruttore deve essere disattivato.
2. Fai scegliere all'utente tra merge in `main` in locale, push con apertura di una PR, o lasciare il branch. La scelta è ancora aperta.
3. Per andare in produzione:
   - `npm run push:keys`;
   - imposta `VAPID_PUBLIC_KEY` e `VAPID_SUBJECT` in `wrangler.jsonc`;
   - `npx wrangler secret put VAPID_PRIVATE_KEY`;
   - `npm run db:migrate:remote`;
   - `npm run deploy`;
   - accendi la push sul client dalla dashboard.
4. Se vale la pena, fai un giro breve sulle rifiniture rimandate, partendo dalla frase di `api-reference.md:75`.

## Da sapere prima di toccare qualcosa

- **`wrangler.jsonc` è ignorato da git.** Ogni modifica di configurazione va in quel file e in `wrangler.jsonc.example`. Dopo, `npm run typecheck` rigenera i tipi.
- **I test non devono raggiungere servizi push reali.** Inietta sempre `PushFetch`: `vi.mock` non funziona nel pool Workers. Usa `pushCall`/`pushRecorder` e `pushEnv`, che contiene le chiavi di test prese dall'esempio della RFC 8291.
- **Alcuni test di `push-send` sono lenti, ed è normale.** Durano circa 1,5 s ciascuno per via del backoff reale da 500 e 1000 ms.
- **Le chiavi VAPID non vanno ruotate se non sono compromesse.** Tutti i browser dovrebbero iscriversi di nuovo.
- **Su iPhone le push funzionano solo con la webapp aggiunta alla schermata Home** (iOS 16.4+).
- **Lo spazio di lavoro `.superpowers/sdd/2026-10-25-web-push/` è ancora su disco,** perché un hook ha bloccato `rm -rf`. È ignorato da git e contiene il registro con l'elenco completo delle rifiniture rimandate. Si può cancellare quando non serve più.
