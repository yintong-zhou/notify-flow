# Cloudflare Email Notification Service

## Objective

This project aims to build a centralized backend service for sending transactional emails and application notifications, running on **Cloudflare Workers**.

The service must be reusable across multiple applications and systems, exposing a **REST API** that lets authorized backends request email delivery without having to integrate SMTP logic directly into each project.

The idea is to create a proprietary, configurable service that is independent of transactional email platforms such as Resend, SendGrid, Mailgun, or equivalent services.

---

## Main use cases

The service must support transactional emails such as:

- welcome email after registration;
- email address verification;
- password recovery;
- password change confirmation;
- login alert from a new device;
- suspicious login;
- operational confirmations;
- updates on the status of an order or process;
- administrative notifications;
- automatic communications generated by the application.

In the future, the service may also be extended to Web Push notifications.

---

## General architecture

```text
Frontend
   |
   | operation request
   v
Backend / Auth Service
   |
   | authenticated request
   v
Cloudflare Email Notification Service
   |
   | template selection
   | validation
   | client authentication
   | SMTP selection
   v
SMTP Provider
   |
   +--> Gmail / Google Workspace
   +--> Microsoft 365
   +--> Custom SMTP
   |
   v
Recipient
```

The frontend must not be responsible for directly sending sensitive emails.

For example, for password recovery:

```text
Frontend
   |
   | POST /forgot-password
   v
Backend / Auth Service
   |
   | generates token
   | validates user
   | builds reset URL
   v
Notification Service
   |
   | password-reset template
   v
SMTP
   |
   v
User email
```

The Notification Service must therefore handle only the delivery of the communication, not the application's authentication or security logic.

---

## Service responsibilities

The service must:

- receive authenticated REST requests;
- validate the payload;
- identify the requested template;
- render the subject, HTML, and plain-text version;
- select the configured SMTP provider;
- open an SMTP connection;
- use TLS or STARTTLS;
- authenticate with the SMTP server;
- send the message;
- handle errors and retries;
- record the status of the operation;
- apply rate limiting;
- protect SMTP credentials;
- prevent unauthorized use of the service.

## API

The first version can expose a single main endpoint:

```http
POST /v1/email/send
```

Example:

```json
{
  "template": "password-reset",
  "to": "utente@example.com",
  "locale": "it",
  "variables": {
    "name": "Mario",
    "resetUrl": "https://app.example.com/reset-password?token=..."
  }
}
```

Response:

```json
{
  "id": "msg_123",
  "status": "accepted"
}
```

A more abstract API can be introduced later:

```http
POST /v1/notifications
```

Example:

```json
{
  "event": "auth.password_reset",
  "recipient": {
    "email": "utente@example.com"
  },
  "data": {
    "name": "Mario",
    "resetUrl": "https://app.example.com/reset-password?token=..."
  }
}
```

The service will resolve internally:

```text
auth.password_reset
        |
        v
password-reset template
        |
        v
SMTP provider
        |
        v
email
```

## Email templates

The service should use predefined templates instead of allowing the frontend to send arbitrary HTML.

Initial examples:

```text
welcome
verify-email
password-reset
password-changed
login-alert
generic-notification
```

Each template may contain:

```text
subject
html
text
allowed variables
locale
```

This keeps branding, copy, translations, layout, security, and versioning centralized.

## SMTP support

The system must be designed as a generic SMTP client and not be tied exclusively to Gmail.

Conceptual configuration:

```text
SMTP_HOST
SMTP_PORT
SMTP_SECURITY
SMTP_AUTH_TYPE
SMTP_USERNAME
SMTP_PASSWORD
SMTP_FROM_EMAIL
SMTP_FROM_NAME
```

### Gmail / Google Workspace

```text
host: smtp.gmail.com
port: 465
security: tls
```

or:

```text
host: smtp.gmail.com
port: 587
security: starttls
```

### Microsoft 365

```text
host: smtp.office365.com
port: 587
security: starttls
```

### Generic SMTP

```text
host: smtp.example.com
port: 587
security: starttls
username: ...
password: ...
```

## Provider abstraction

The application logic must not depend directly on Gmail or Microsoft.

```text
Email Service
     |
     v
SMTP Adapter
     |
     +--> Gmail preset
     +--> Microsoft preset
     +--> Generic SMTP
```

Gmail and Microsoft can therefore be treated as configuration presets on top of a generic SMTP client.

## SMTP Client

The SMTP client must handle at least:

```text
TCP connection
EHLO
STARTTLS
AUTH LOGIN
AUTH PLAIN
MAIL FROM
RCPT TO
DATA
QUIT
```

It must also support:

```text
Implicit TLS
STARTTLS
```

In the future, the following may be added:

```text
OAuth2 / XOAUTH2
```

for providers such as Microsoft 365 and Google Workspace.

## Security

The service must not be publicly usable without authentication.

Each authorized application should have its own API key.

```http
Authorization: Bearer SERVICE_API_KEY
```

or:

```http
X-API-Key: SERVICE_API_KEY
```

API keys must not be stored in plain text in the database.

For a more advanced version, HMAC signatures can be used:

```text
X-Client-Id
X-Timestamp
X-Signature
```

with the signature computed as:

```text
HMAC-SHA256(timestamp + request_body, client_secret)
```

---

## SMTP credential management

SMTP passwords must not be:

- placed in the frontend;
- present in the repository;
- hardcoded in the code;
- saved in public files;
- included in logs.

For a simple setup, credentials can be stored via **Cloudflare Secrets**.

If the service later needs to support multiple dynamic SMTP accounts or multiple customers, credentials can be stored encrypted in a database, keeping the master encryption key in Cloudflare Secrets.

---

## Separation between frontend and backend

For sensitive endpoints, the frontend must not be able to send arbitrary requests such as:

```json
{
  "to": "qualunque@email.com",
  "subject": "test",
  "html": "<h1>...</h1>"
}
```

Instead, the frontend must request an application action, for example:

```text
forgot-password
register
change-email
login
```

The backend verifies the operation and, if valid, calls the Notification Service.

This prevents spam, abuse of the service, impersonation, arbitrary email sending, and template manipulation.

---

## Rate limiting

The service must implement configurable usage limits.

Example:

```text
password-reset:
5 requests per email / hour

API client:
100 requests / minute
```

---

## Idempotency

Sensitive requests should support an idempotency key.

```http
Idempotency-Key: password-reset:user-123:request-456
```

If the same request is sent multiple times, the service must avoid sending duplicates.

---

## Logging

Each send request can produce an internal record:

```text
email_deliveries
----------------
id
request_id
client_id
template
provider
recipient
status
created_at
sent_at
attempts
error_code
```

Passwords, sensitive tokens, SMTP credentials, and plain-text reset tokens must not be stored in logs.

---

## Statuses

The recommended statuses are:

```text
accepted
queued
processing
submitted
failed
retrying
```

A positive response from the SMTP server means the message has been accepted by the SMTP server, not necessarily delivered to the recipient's inbox. For this reason, it is preferable to use `submitted` instead of `delivered` until a true delivery tracking system is implemented.

---

## Cloudflare Queues

After the first MVP, sending should become asynchronous.

```text
Backend
   |
   | REST request
   v
API Worker
   |
   | validation
   | authentication
   | enqueue
   v
Cloudflare Queue
   |
   v
Email Worker
   |
   | template rendering
   | SMTP
   | retry
   | logging
   v
SMTP Provider
```

The REST API can thus respond quickly with `202 Accepted` and a `queued` status.
